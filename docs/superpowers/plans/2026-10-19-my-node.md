### C. Auto-advert (decided: dropped)

The Advert activity card has no Auto advert row, and nothing is built for it (see §0: there is no data source).

### D. "Forget this radio" (decided: dropped)

- There is no Forget button in the page header or in the disconnected card's Remembered row.
- The existing Forget actions on the Radio Connection page go away with that page, and `clearLastDevice()` in `lib/lastDevice.ts`, whose only callers are there, is deleted.
- The only way a cached radio leaves the node cache is eviction: the least recently seen radios beyond **5 entries** are evicted (see "Last-known node cache"), so plaintext lat/lon and adverts aren't kept for every radio ever connected.

## Answers to the open questions

### 1. Does self-telemetry transmit over RF?

**No. It is answered locally, so live polling is allowed.**

- Firmware `examples/companion_radio/MyMesh.cpp` @ `d929643`, lines 1651–1670: `CMD_SEND_TELEMETRY_REQ` with `len == 4` is the "'self' telemetry request".
  - It fills `telemetry` with battery volts, MCU temperature (when not NaN), and `sensors.querySensors(0xFF, …)`.
  - It writes `PUSH_CODE_TELEMETRY_RESPONSE` (0x8B) `[0x8B][0][6-byte self prefix][LPP]` **straight to the serial/BLE interface** with `_serial->writeFrame`.
  - It never builds a `mesh::Packet`, never calls `sendFlood`/`sendDirect`, and never calls `clearPendingReqs()`. So it doesn't kill a pending repeater request either. Compare line 1631, the remote branch, which does both.
- meshcore-ts 0.9.0 `requestSelfTelemetry()` sends `[0x27,0,0,0]` and resolves on the 0x8B frame whose prefix matches the owner (5 s default timeout). Older firmware answers `ERR_CODE_UNSUPPORTED_CMD`, which the library maps to a "self telemetry unsupported" `ProtocolError`. On that error we stop polling and show the card as unsupported.
- Remaining cost:
  - `querySensors` may read I²C sensors.
  - On GPS boards it reports the cached fix.
  - Each poll is one round-trip on the BLE link.

  At 10 s this is negligible on the radio side. Polls do not take #61's **mesh** lock, which guards RF requests. The BLE link is a separate concern; see the next section.

#### Sharing the BLE link with user commands

meshcore-ts does **not** queue commands. `MeshCoreSession.request`/`requestOrError` write the frame at once and correlate replies through a per-response-code waiter queue plus a shared ack FIFO ordered by write sequence (`dist/index.js` 5785–5860 in 0.9.0). The firmware handles one command frame at a time and replies in order. Commands therefore pipeline safely: a user send's `RESP_OK` never satisfies a poll waiter, because typed waiters are `errOnly` on the ack FIFO. However:

- **`repeaterGetLocalStats` holds one pending slot and rejects the previous call with "superseded by newer GET_STATS"** (`dist/index.js:4499`). The three stats subtypes must therefore run **one after another**, never as a burst.
- A user command written right behind a poll burst waits for the poll replies. Typed requests time out at `REQUEST_TIMEOUT_MS` = 5 s, which a slow BLE link plus a 4-frame burst should never reach. It still adds latency, so the poller stays out of the way, as follows.

Rules for the poller:

1. **At most one poll frame in flight.** Each tick sends self-telemetry, then core stats, then radio stats, then packet stats, awaiting each before the next. This is a staggered sequence, not a burst, so a user frame can slot in between any two of them.
2. **Skip the tick while a user command is in flight.** A small main-side `userCommandGate` (Hono middleware) counts in-flight mutating `/api/*` requests (POST, PUT, PATCH, DELETE), excluding the two poll routes. The poll routes check it **before each frame**. If the gate is busy they stop and return `409 { code: 'busy_skip' }`. The poller treats that as a skipped tick: no error, no "Updated" reset, and a retry at the next interval. #61's mesh lock counts as busy too.
3. **Single-flight across the page.** The poller never overlaps itself, and stats for one tick come from one `/api/device/stats` call.
4. **Stats cadence.** Stats ride the same 10 s tick. If you'd rather lighten the link, stats could run every third tick (30 s) while telemetry stays at 10 s. That's a one-line change in `poll.ts`, so I'm not making it a decision.

### 2. Does v1.17.1 support the stats command, and what does it return?

**Yes.**

- `CMD_GET_STATS` (56) is gated "v8+". At `d929643`, `FIRMWARE_VER_CODE` is **13** (`MyMesh.h:8`). The handler is at `MyMesh.cpp:1865–1916`. Every reply is `[RESP_CODE_STATS][subtype]…`, little-endian:

  | Subtype | Fields |
  |---|---|
  | `CORE` (0) | `battery_mv` u16, `uptime_secs` u32 (millis/1000, since boot), `err_flags` u16, `queue_len` u8 |
  | `RADIO` (1) | `noise_floor` i16 dBm, `last_rssi` i8 dBm, `last_snr` i8 ×4 (0.25 dB steps), `tx_air_secs` u32, `rx_air_secs` u32 |
  | `PACKETS` (2) | `recv`, `sent`, `n_sent_flood`, `n_sent_direct`, `n_recv_flood`, `n_recv_direct`, `n_recv_errors`, all u32 |

- The library has had this since 0.8.1 as `repeaterGetLocalStats(subtype)`, returning `LocalStats` with `lastSnrDb` already divided by 4.
- CoreSense already exposes it as `POST /api/repeater/local/stats` (`routes/repeater.ts:166`). Nothing in the UI uses it, so this plan replaces it with `/api/device/stats` (see Architecture).
- The library keeps **one pending** `GET_STATS` and rejects an overlapping call as "superseded", so the three subtypes are always read in sequence.
- Support check: hide the card when `deviceInfo.firmwareVerCode < 8`, or when the first call rejects with `UNSUPPORTED_CMD`.

### 3. Is the last self-advert time readable from the radio?

**No. CoreSense must track it.**

- `CMD_SEND_SELF_ADVERT` (`MyMesh.cpp:1250`) builds and sends the packet and replies only `RESP_OK`.
- No SELF_INFO, DEVICE_INFO, or stats field records when the node last adverted.
- The on-device button path (`MyMesh::advert()`, line 2249) is invisible to the app.

Plan:
- Record `{ at, flood }` in main whenever `POST /api/transport/advert` succeeds. This route is the single path used by quick actions, the palette, the card buttons, and the console.
- Persist it in the node cache.
- Label the row "Last self-advert from CoreSense" in the row's `title`, so nobody reads it as authoritative for button presses on the radio itself.

### 4. Where should the poll interval be configured?

**Fixed at 10 s for now**, as `SELF_POLL_MS = 10_000` in `features/my-node/poll.ts`. The read is local and cheap, the "Updated N s ago" timer tells the user everything a setting would, and an App setting adds UI, schema, and docs for a knob nobody has asked for. It is easy to promote to `AppSettings` later; the poller takes it as a parameter.

### 5. Is the Radio Connection UI reusable?

**Partly. It needs extracting.**

`panels/BleConnect.tsx` is a single 300-line panel with fixed panel chrome (`lg:w-96`, its own header), the removed "Live link" card, and internal sub-components that aren't exported.

Plan:
- Extract `TransportTabs`, `StatusLine`, `ScanButton`, `DeviceList`, and a reworked `RememberedRow` into `features/connection/`. The scan, connect, and disconnect handlers still come from `App.tsx` through `MainPane` props, as they do now.
- Restyle `TransportTabs` to the rail recipe: `bg-cs-bg-3` track, selected `bg-cs-bg text-cs-accent`.
- Compose them into `RadioConnectionCard` for the disconnected grid.
- Delete `BleConnect.tsx` once nothing renders it. The "Live link" card goes. Disconnect moves to the page header. Forget is dropped (Decision D).

#### Write validation

These rules live in `shared/` as pure functions. The zod schemas call them, so every caller hits the same rejection: Radio Settings, PublicInfo, the Location card, the console, and any direct API client.

- **Lat/lon** (`shared/geo.ts` `validateLatLon`, `parseCoord`): lat in `[-90, 90]`, lon in `[-180, 180]`, finite, at most 5 decimal places. Blank is rejected (clearing a position is not a My Node action). This mirrors the firmware's own range check (`MyMesh.cpp:1226`).
- **TX power** (`shared/radio.ts` `validateTxPower(dbm, limits)`): an integer in `[radioLimits.minTxPowerDbm, radioLimits.maxTxPowerDbm]`. These are the firmware's own bounds: `CMD_SET_RADIO_TX_POWER` rejects anything outside `-9..MAX_LORA_TX_POWER` (`MyMesh.cpp:1417`). This replaces Radio Settings' hard-coded `-3..22`, and the UI will show the radio's real range. The server reads `maxTxPowerDbm` from the holder's `radioLimits`, never from the request.
- **Name** (`shared/radio.ts` `validateNodeName`): trim surrounding whitespace, apply Unicode NFC, then reject an empty name, any C0/C1 control character, or more than **31 UTF-8 bytes**. Firmware stores `char node_name[32]` (`NodePrefs.h:15`) and `CMD_SET_ADVERT_NAME` silently truncates past 31 bytes (`MyMesh.cpp:1212–1218`), which could cut a multi-byte character in half. The byte check runs on the normalised string, which is what gets sent.

#### Last-known node cache

The cache lives in `node-cache.json` as `{ version: 1, entries: Record<publicKeyHex, NodeCacheEntry> }`. The loader is tolerant, like the other store files: a missing or unknown `version`, a malformed entry, or an unknown field drops back to defaults for that entry instead of failing the load. Future shape changes bump `version` and migrate in the loader. Each entry holds:

- `identity` (name, publicKeyHex, lat, lon, sharePositionInAdvert)
- `deviceInfo`, `radioSettings`, `gpsConfig`
- `bleId` (the renderer already remembers the BLE name in `lastDevice`)
- `advertLinkHex`
- `lastSelfAdvert` `{ at, flood } | null`
- `lastLive` `{ at, rawHex } | null`
- `lastConnectedAt` and `lastSeenAt`

When it is written:
- On every `commit.deviceIdentity`, `radioSettings`, `gpsConfig`, and `deviceInfo` while connected.
- On a live telemetry read, throttled to at most one write per 60 s plus a write on disconnect, so the 10 s poll doesn't rewrite the file every tick.

Invalidation and eviction:
- **The advert link is invalidated on every `commit.deviceIdentity`.** The link is a signed advert that embeds the name, lat/lon (when shared) and a timestamp. So a name change, a position save (Location card, console, PublicInfo), or the share-position toggle sets `advertLinkHex = null`. While connected, main re-fetches it right away. While disconnected, the Identity card shows the QR only when the cached link is still valid; otherwise it shows the public key with "Connect to refresh the advert link".
- **Eviction:** the cache keeps at most **5 entries**, evicting the least recent `lastSeenAt`. This keeps the stored lat/lon and adverts limited to radios used recently. Eviction is the only removal path, since Forget is dropped (Decision D).

This lives in app store files, not radio settings. The existing global `device-identity.json` and `device-info.json` stay as they are, because they serve other screens.

Which entry the disconnected page shows: the entry whose `bleId` matches `loadLastDevice()?.id`, otherwise the most recent `lastSeenAt`.

### Polling lifecycle (`features/my-node/poll.ts`)

The poller is pure. It is created with `{ intervalMs, fetchTelemetry, fetchStats, now, setTimeout }` and runs only when all of these are true:

- the page is mounted;
- `document.visibilityState === 'visible'`;
- `transportState === 'connected'`.

Behaviour:
- It fires once immediately, then every `intervalMs` measured from the end of the previous call, so a slow call never overlaps the next.
- Within a tick it awaits each command before sending the next, and a `409 busy_skip` from either poll route counts as a skipped tick, not a failure (see "Sharing the BLE link with user commands").
- It stops on unmount, when the window is hidden, or on disconnect, and resumes when all three hold again.
- A self-telemetry error of the "unsupported" kind stops telemetry polling only, and the card shows "This firmware can't report its own telemetry".
- Stats-unsupported hides the stats card.
- A transient error keeps polling, and the "Updated N s ago" text turns `cs-warn` after 3 consecutive failures.
- "Updated N s ago" uses `useNowTick(1000)` scoped to the two header labels only.

### Console registry

There is no companion text CLI, so commands are defined app-side:

```ts
interface NodeCommand {
  name: string;                 // 'get radio', 'set tx', 'advert flood'
  group: 'info' | 'radio' | 'position' | 'advert' | 'identity' | 'app';
  args?: CliArg[];              // reuse CliArg from shared/repeater-cli
  desc: string;
  danger?: boolean;             // reuse the hold-to-confirm bar
  run(ctx: ConsoleCtx, args: string[]): Promise<ConsoleOutput>;
}
```

Commands and what each calls:

| Command | Calls |
|---|---|
| `help` | the registry itself |
| `ver` | `deviceInfo` |
| `get name` | `deviceIdentity.name` |
| `get radio` | `radioSettings` |
| `get lat`, `get lon` | `deviceIdentity` |
| `stats radio`, `stats packets` | `/api/device/stats` |
| `clock` | `/api/device/clock` |
| `advert flood`, `advert zerohop` | `api.sendAdvert` (same route as the quick actions) |
| `set name <text>` | `api.putDeviceIdentity({ name })`, validated by `validateNodeName` on both sides |
| `set tx <dBm>` | `PATCH /api/device/radio { txPowerDbm }`: a server-side merge against the holder's `radioSettings`, `validateTxPower` against the radio's reported limits, then the same `applyRadioSettings` path as Radio Settings |
| `set lat <deg>`, `set lon <deg>` | `api.putDeviceIdentity` + `validateLatLon` |

Errors and history:
- An unknown command produces "Unknown command: stat — did you mean stats?", from the first token matched against the first tokens of command names.
- Errors use `<Action> failed: <reason>`.
- History persists per radio via `cli/lib/persistence.ts`, keyed `coresense.console.history.<ownerPubkey>`.

#### Sharing the repeater CLI UI

This refactor lands as **its own PR, before Phase 4**, not inside Phase 1. It changes shipped repeater UI, it is behaviour-preserving and so easy to review alone, and nothing before the console needs it. A regression there therefore can't block My Node. The steps are minimal, behaviour-preserving refactors, each with the existing CLI tests still passing:

1. Make the catalog a parameter. Add a `ConsoleCommand` base type, with `CliCommand extends ConsoleCommand`. Pass `commands` through `parseCliLine`, `resolveCommand`, `suggest`, and the prompt reducer `ctx`. These are the only places that import `CLI_COMMANDS` directly today.
2. Make the repeater-only extras props: `CliPrompt` and `CliPalette` take `chipsFor`, `roundTripFor`, `placeholder`/`aria-label`, `banner` (replacing guest/`onLoginAsAdmin`), and group labels. Make `CliTranscript` empty-state text a prop.
3. Generalise the row model:
   - `CliEntry<C>` gets an optional `kind: 'command' | 'info'`.
   - The glyph column maps to `›` accent for commands, `✓` `cs-online` for OK, `✕` `cs-danger` for errors, `⧗` `cs-warn` for pending, and `·` dim for info.
   - The repeater keeps its own row decorations (superseded, truncated, serial-only) through a `decorate` callback.
4. Leave repeater-only code alone: `send.ts`, `airtime.ts`, `RebootPending`, and the CliTab drain loop. The node console has its own small orchestrator over the existing pure `queue.ts`, where "send" means `registry.run()`.

This deliberately changes the repeater transcript's echo glyph from `$` to `›` so the two consoles match. Flag it if you'd rather keep `$` for repeaters.

## Protocol commands: what exists and what's needed

| Need | Firmware cmd | meshcore-ts | CoreSense today | Work |
|---|---|---|---|---|
| Self telemetry | 0x27, len 4 | `requestSelfTelemetry` (0.9.0) | #61 service (saves every read) | non-saving live route + snapshot route |
| Stats core/radio/packets | 56 | `repeaterGetLocalStats` (0.8.1+; one pending call, so it must be called sequentially) | `POST /api/repeater/local/stats` (unused) | `POST /api/device/stats` via `readLocalStats`; delete the old route |
| Device info, battery/storage | 22, 20 | yes; library polls every 60 s | snapshot + WS | none |
| Radio params read | SELF_INFO | yes | `radioSettings` | none |
| Set lat/lon | 14 | `setAdvertLatLon` | `PUT /api/device/identity` | server range validation |
| GPS on/off | custom vars | `setGpsConfig` / `setCustomVar` | `PUT /api/device/gps` | none |
| Share position in advert | 38 | `setOtherParams` | `PUT /api/device/identity` | none |
| Self advert | 7 | `sendSelfAdvert(flood)` | `POST /api/transport/advert` | record `lastSelfAdvert` |
| Self contact export (QR) | 17, no key | `exportContact()` | — | `GET /api/device/advert-link` |
| Device clock | 5 | `getDeviceTime()` | — | `GET /api/device/clock` |
| Set name / TX | 8 / 11–12 | yes | identity / radio routes | shared validators; `PUT /api/device/radio` partial update |
| Max TX power | SELF_INFO byte 3 | `getSelfInfo().maxTxPowerDbm` | not stored | `radioLimits` holder field |

The QR encodes `meshcore://<self-advert packet hex>`. That is the format `lib/meshcoreUri.ts` already decodes, and the comment there notes the official apps emit it. Because it is a signed advert from the radio, it can't be built offline. That is why it is cached, which keeps the Identity card working while disconnected.

## Phase 1 as built

Phase 1 landed as six commits on this branch, with lint, typecheck and the full suite green. It differs from the plan in a few small ways:

- **`PUT /api/device/radio`, not PATCH.** It keeps partial semantics, like `PUT /api/device/telemetry-policy` ("a PATCH in all but verb"). The server's CORS rule doesn't allow PATCH, and the renderer client has no PATCH helper.
- **`radioLimits` is read passively.** The board's `MAX_LORA_TX_POWER` comes from byte 3 of the handshake's own RESP_SELF_INFO on the packet bus (`main/device/radioLimits.ts`). Calling `getSelfInfo()` would re-send APP_START, which stops a contact walk in progress.
- **Decimal places.** The server enforces the coordinate range only. The radio stores 6 decimal places, so PublicInfo accepts 6; only My Node's own fields (and the console) cap input at 5.
- **PublicInfo sends only what changed.** The name and the position are sent only when edited, so an identity with no name yet can still save its position.
- **A node-cache entry opens on `commit.owner`, never at link-up.** At link-up the holder's owner can still be the previous radio's.
- **The node cache doesn't store `bleName`.** The renderer's `lastDevice` already has it.
- **The poller resets "unsupported" on reconnect.** The next radio may support what the last one didn't.
- **The command gate counts only radio-facing routes.** App-only writes (drafts, UI state, macros, block rules) don't count, or every poll would be skipped while someone types.
